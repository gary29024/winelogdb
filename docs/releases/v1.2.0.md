# WineLogDB v1.2.0

**Release date:** 2026-09-15

WineLogDB 1.2 makes the journal substantially more useful after the bottle has been logged. It adds **Smart Search** for descriptive natural-language retrieval, expands vintage lookup into source-aware **Vintage Intelligence**, makes paid vintage research durable through the existing Cloudflare queue, and adds release-specific Champagne/sparkling details with photo backfill for bottles already in the journal.

The release also adds shareable 9:16 tasting/story cards, improves producer-range refresh cost and resilience, makes wine saves more transactional, persists private thumbnails in R2, and fixes a broad set of real-use issues across Journal search, Batch/Group Scan, imagery, Champagne classification and mobile forms.

## Highlights

### Find a wine by what it was like, not only what it was called

Journal search keeps its existing fast D1 FTS/structured path, but descriptive queries can now opt into **Smart Search**.

- Normal typing still uses the cheap lexical path after the existing debounce; pausing in the search box does **not** buy an embedding call.
- An explicit **Smart search** action embeds the query and combines semantic candidates with the canonical Journal filters, pagination and sorting.
- The default provider is Cloudflare Workers AI `@cf/qwen/qwen3-embedding-0.6b`, so the standard configuration needs no additional API key. Gemini `gemini-embedding-001` remains an optional BYOK provider.
- Wine embeddings are stored as normalized Float32 vectors and refreshed in background work after relevant edits. A stale-but-valid vector remains searchable until its replacement is ready.
- If the embedding provider is unavailable, the Journal fails open to ordinary lexical search rather than making the Journal unusable.
- Production D1 BLOB decoding and the D1 variable-limit paths were hardened after rollout. Semantic result sets are packed safely instead of binding candidate IDs repeatedly, and existing stored embeddings remain valid.

This is deliberately a hybrid search rather than replacing exact search: a producer, vintage or appellation is still best served by the existing lexical/structured path, while phrases such as *floral elegant Pinot* can use meaning as another retrieval signal.

### Vintage lookup becomes Vintage Intelligence

The existing on-demand, grounded vintage lookup now returns a broader evidence-led assessment without creating a second research system or cache.

- A researched vintage can receive a **WineLog estimate from 70–100**, a quality band, AI-assessed confidence, consensus, strengths and cautions.
- The estimate is explicitly WineLog's synthesis, not a copied critic score. The prompt uses publicly accessible regional, critic, merchant and harvest commentary and does not present a third party's numeric rating as WineLog's own.
- Evidence/source links stay attached to the result, and a quality assessment can still be useful when the evidence is insufficient to justify a precise drinking-window shift.
- The cellar leads with researched drinking readiness when available and keeps the normal rule-of-thumb window as context. A compact Vintage Intelligence dialog exposes the evidence without making another automatic AI request.
- Tasted-wine detail pages no longer spend a maturity request answering “should I open this?” after the bottle has already been consumed; the feature remains enabled for the cellar and can be switched back on for wine detail with one surface flag.

Vintage research is also now **queue-backed**. Once a new lookup or refresh is accepted, closing the browser does not cancel the paid work. Owner/vintage-cell jobs are persisted and deduplicated, queue redelivery cannot start a second paid attempt, and a failed refresh preserves the previously saved result. The browser observes status for a bounded period; the accepted job itself belongs to the queue rather than to that browser connection.

### Capture the facts that belong to one Champagne release

Champagne and other traditional-method sparkling wines can now store release-specific technical details on the individual logged bottle rather than incorrectly turning them into permanent cuvée attributes.

The compact sparkling section can hold dosage, dosage style, disgorgement, tirage/bottling, base vintage, reserve-wine percentage, lees ageing, lot/release code, assemblage, reserve-wine detail, malolactic information, fermentation/elevage and other technical notes. Single-wine multi-photo recognition can populate those fields when they are **explicitly visible on the supplied labels**; the recognition prompt forbids inferring precise values from general producer or cuvée knowledge.

For Champagne already in the Journal, **Fill Champagne details from photos** can stage a background extraction from up to six saved bottle photos. Suggestions are persisted separately and are not silently written into the wine: **Add suggestions to form** fills only empty fields, and the normal atomic wine Save is still the operation that applies them.

The eligibility logic now handles the way Champagne is actually recorded: village names such as Ambonnay, Bouzy and Aÿ can sit in the appellation field, `Champagne Grand Cru` and `Champagne Blanc de Blancs` are recognised, and rosé Champagne is eligible. Still/fortified wines from the region such as Coteaux Champenois, Rosé des Riceys and Ratafia remain excluded, as do non-Champagne sparkling wines.

### Share a tasting as a story card

A tasting or selected Journal lineup can now become a **1080 × 1920** label collage designed for a phone share sheet and Instagram Stories.

- Choose up to 16 wines from the lineup without going back to Journal selection.
- The layout measures available space and chooses the grid that keeps labels largest while preserving a portrait story composition.
- Favourites receive a small star; wines without a photo get a visual fallback rather than an empty hole.
- Date and tasting name are independently optional, and the photo grid automatically expands into the space freed when either is hidden.
- On browsers that support file sharing, the card goes to the native share sheet. Unsupported environments fall back to saving the generated card.

No direct Instagram-posting API is claimed or required; the phone's native share sheet is the integration boundary.

### Cheaper producer-range refreshes when the official site is enough

Producer range/catalogue refreshes can now avoid a full grounded search when WineLog already has a fresh producer profile and useful official-source URLs.

The Phase 2 path reuses/crawls a small set of same-domain official pages, then attempts structured extraction with GLM-4.7-Flash through Cloudflare AI Gateway / Z.AI. A separately hosted Workers AI copy provides resilience for provider/model failure. WineLog commits that cheap-path result only when the official evidence appears complete and the catalogue passes conservative coverage checks; otherwise the existing grounded Gemini + Google Search workflow remains the fallback.

Manual catalogue corrections are durable across future refreshes. **Add missing wine** stores user-confirmed catalogue rows outside the replaceable machine-researched base, while incomplete evidence can surface **Possible missing wines** for review instead of silently rewriting the producer range.

### More reliable saves and smaller private image reads

Wine create/edit reliability and photo delivery received a deeper infrastructure pass.

- Wine data, supplied photo rows, tasting state, latest experience, live-tasting activity and optional tasting structure are committed in one D1 batch for the normal JSON/multipart save paths. Database failure rolls that batch back rather than reporting a partially completed save.
- Failed multipart creation removes R2 objects uploaded for that attempt.
- Small wine-card images use an authenticated private thumbnail path. A generated WebP fits within 640 × 640 without cropping/enlargement and can be retained at `thumb/v1/...` in the existing private R2 bucket.
- Every thumbnail request still verifies ownership in D1 before cache/R2 delivery; the derivative cache cannot bypass authorization.
- Existing photos need no migration or bulk backfill: the persistent thumbnail is generated on first uncached use where Cloudflare Images is available, with safe fallback to the original.

This keeps the original image for full-size viewing and sharing while reducing repeated R2 transfer/decoding work for ordinary card grids.

### Scanning, Journal and mobile polish

A set of real-use fixes landed alongside the larger features:

- Group Scan no longer discards an otherwise valid recognition merely because a non-essential bounding-box coordinate is missing; alternate coordinate shapes and safe full-height fallback are accepted while invalid/inverted boxes remain rejected.
- Automatically matched tasting-sheet wines are treated as claimed, preventing another row from assigning itself to the same wine.
- Photographed tasting-sheet pages are visible as local thumbnails before AI reading, so the user can inspect the evidence before spending on recognition.
- Producer-page tasted cuvées are sorted alphabetically instead of by whichever bottle was drunk most recently.
- Spirits such as Calvados can store realistic alcohol percentages, and Batch Scan now shows the actual invalid field instead of reducing validation errors to a generic “Invalid wine”.
- Journal semantic candidate queries and `/api/wines?limit=100` no longer exceed D1's SQL-variable ceiling.
- Mobile `input`, `select` and `textarea` fields consistently meet the 16 px anti-zoom threshold, including the compact sparkling grid.

For a self-hosted deployment, back up D1/R2 as appropriate and use the repository-supported command:

```bash
npm run deploy
```

That command builds the application, applies outstanding **remote D1 migrations**, and only then deploys the Worker. Do not substitute a bare `wrangler deploy` for this upgrade.

Additional configuration notes:

- Smart Search defaults to the Workers AI binding already declared in `wrangler.jsonc`; no extra API key is required for the default provider. See `docs/semantic-search.md` for optional Gemini BYOK and the point at which Vectorize should be reconsidered for a much larger journal.
- Producer Range Phase 2 can use an AI Gateway custom provider named `zai` with its provider key stored in Gateway BYOK. A Worker secret named `ZAI_API_KEY` alone is not used by this path. See `docs/producer-range-phase2.md`.
- Private thumbnail generation uses the Cloudflare Images binding when available and retains generated derivatives in private R2. Confirm the Cloudflare Images plan/allowance appropriate to the deployment; the app does not change account billing plans.
- Existing open browser tabs from an older deployment should be reloaded after upgrade so they understand the queued vintage-research `202`/status-observation protocol.

## Notes worth knowing

- **Smart Search is opt-in.** Ordinary Journal typing remains lexical/structured and does not purchase an embedding call merely because the user pauses.
- The semantic index can warm in background work. A cold/partial Smart Search stays retryable rather than claiming the index is complete.
- Vintage quality numbers are **WineLog estimates**, not critic scores, and confidence remains AI-assessed rather than a deterministic count of independent publishers.
- Queued vintage research survives the browser observer ending, but an unexpected interruption of an already-running paid provider attempt is not silently replayed as another paid call; recovery remains explicit.
- Champagne photo extraction stages suggestions only. It does not overwrite existing release details and it does not infer facts that are not readable in the saved photos.
- Persistent thumbnails preserve the private-original model: authentication/ownership is checked before derivative delivery, and full-size views/story exports still use the original.
- Multi-user accounts, friend sharing and AI credit controls remain in draft PR #224 and are outside this release boundary.
