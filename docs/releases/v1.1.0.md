# WineLogDB v1.1.0

**Release date:** 2026-09-03

WineLogDB 1.1 is the first feature release after the v1.0.0 stable baseline. It consolidates every merged product PR after v1.0.0 through PR #207, with the largest addition being a true **cellar** for bottles you own but have not yet drunk, plus drinking-window guidance and on-demand vintage research.

The release also expands Wine Collections, makes the Passport map more geographically honest, improves grape/tag semantics, reduces repeat R2 reads and fixes several Journal, Batch Scan, vintage-research and cost-accounting issues found in real use.

## Highlights

### Keep the cellar separate from the drinking journal

WineLogDB can now hold bottles that are **owned but unopened** without pretending they have already been tasted.

- A new **In cellar** Journal scope is separate from **Tasted** and Favorites.
- Cellar holdings live in their own data model, so adding a case does not increase tasted-wine counts, producer experience, Passport progress, Insights statistics or achievement progress.
- Add holdings by producer/cuvée, vintage, format, quantity, purchase price/currency, merchant and storage location.
- Existing producer and cuvée identities can be reused, but entering an unopened bottle does not create an untasted producer/cuvée profile just to make the cellar work.
- Producer matching now gives the same exact/near-miss help used by the scan form, reducing spelling drift before a bottle eventually enters the journal.
- Holdings can be corrected later through a compact mobile edit sheet.

When you open a bottle, WineLogDB uses the normal wine form. The holding is decremented **only after the wine saves successfully**, its purchase price follows into the wine record, and an optional label photo can be checked for disagreements before you accept any correction.

### Know when a bottle is worth opening

The cellar now answers the practical question that motivated it: **is this bottle ready?**

Every vintage wine can receive a free calculated window based on the place hierarchy, style and cru tier. This is explicitly presented as a rule of thumb rather than research. Burgundy grand cru is treated differently from a village wine, and a curated set of long-lived prestige Champagnes receives cuvée-specific baselines instead of inheriting the generic Champagne window.

For a particular vintage, **Look up [year]** runs a grounded Google Search/Gemini assessment only when requested. The researched vintage shift sits beside the normal window instead of replacing it, shows its sources, and is cached so the same underlying vintage question does not need to be bought repeatedly.

The lookup became more robust across the follow-up PRs in this release:

- named Burgundy grand crus can have site-specific vintage cells while broader wines continue to share regional context;
- lower-cost `gemini-3.1-flash-lite` is tried first and `gemini-3.7-flash` is used only when grounding/provider/response quality requires escalation;
- grounded replies wrapped in prose, code fences or trailing citation text can still be parsed safely;
- truncation is reported separately from an unreadable answer;
- failed and successful attempts are metered consistently; and
- the app identifies the model that actually answered and reloads affected cellar rows immediately after a lookup lands.

### Wine Collections gain benchmark producers and named cuvées

The curated achievement set grows with four substantial additions:

- **Primum Familiae Vini · The 12 Families**
- **Napa Valley · 17 Nested AVAs**
- **Willamette Valley · 11 Nested AVAs**
- **World Benchmark Producers & Cuvées** — 143 course-derived tasting targets inside one regionally organised card

The benchmark collection deliberately distinguishes a producer example from a specifically named wine. If the course names only a producer, an appropriately linked wine from that producer can complete the row. If the course names a cuvée — for example **Clos la Néore, La Turque, La Mouline, La Landonne, La Chapelle, Les Bessards, Único, Gran Reserva 904, Viña Tondonia, Sassicaia, Masseto, Solaia, Yattarna, Hill of Grace, Cask 23 or Columella** — that cuvée is the target.

A different wine from the same producer therefore cannot complete a named-cuvée goal, and the specific cuvée replaces the broad producer row so one bottle does not earn two artificial ticks.

### Passport maps wine regions where one country dot is misleading

Passport previously used one anchor per country. That is reasonable for compact European wine countries but misleading for places where major regions are thousands of kilometres apart.

WineLogDB can now spread large wine countries into canonical region markers where the geography warrants it, including the United States, Australia, Canada, Argentina and New Zealand. Unknown/unmapped regions fall back to the country marker rather than being placed somewhere invented.

The region payload is also no longer truncated before the map sees it, so a Margaret River or Finger Lakes entry cannot disappear merely because twenty higher-volume regions came first.

### Grapes and tags follow the wine without rewriting the label

A journal may contain the same grape under regional names — Pinot Noir, Pinot Nero, Spätburgunder and Blauburgunder, for example. Those spellings are now **folded for counting and filtering**, while the wording on each bottle remains the wording you recorded.

Passport and Insights therefore produce one meaningful count instead of several fragments, and Journal grape filters follow the same synonym group. Style-significant distinctions such as Syrah/Shiraz and Pinot Gris/Pinot Grigio remain separate by design. The wine form also offers local grape-name suggestions without making an API call.

Derived tags now move with a corrected wine. If country, region, appellation, grape or style changes, stale generated tags are removed and new generated tags are added, while hand-written tags are preserved and a generated tag you deliberately deleted is not resurrected on a later edit.

### Faster Journal and fewer repeated image reads

Several post-1.0 performance fixes reduce work that was visible on mobile or unnecessary on Cloudflare:

- Journal Reset no longer resurrects a remembered search after the field has been cleared.
- Search typing stays inside a small local input and only the settled query updates the URL/API, so rapid typing no longer re-renders an entire page of wine cards per character.
- Existing Journal results stay painted while a new query is loading.
- D1 now has an expression index for the Journal's real chronological sort, `coalesce(tasting_date, created_at)`.
- Batch Scan retries transient R2 same-object throttling (`10058`) instead of turning it into a false permanent failure.
- Batch Scan previews and Group Photo source/preview/crop images reuse bounded in-memory blobs and collapse concurrent same-image requests, reducing repeat private R2 reads.
- Wine/producer research elapsed timers update in a small leaf component instead of re-rendering the full detail page every second.
- Passport/Insights/achievement client caches are invalidated immediately after relevant writes instead of remaining stale for the local cache window.

### More accurate AI cost reporting and gateway-only operation

The monthly AI rollup now retains the **model and service tier** that produced each usage row. This fixes a mismatch where detailed workflow cards could be priced correctly but the billing-month total repriced mixed usage at a fallback model.

The month tile now says that it is the **billing month**, distinguishes token spend from the grounding-search allowance/cost, and keeps enough decimal precision for tiny recognition costs.

A fully configured Cloudflare AI Gateway / Vertex deployment no longer requires a direct `GEMINI_API_KEY`. Incomplete gateway configuration fails explicitly rather than silently falling through to a direct request with no credential.

## Deployment / upgrade

This release contains four D1 migrations after the v1.0.0 baseline:

- `0044_journal_date_index.sql`
- `0045_cellar_holdings.sql`
- `0046_vintage_windows.sql`
- `0047_ai_usage_monthly_model.sql`

For a self-hosted deployment, back up D1/R2 as appropriate and deploy with the repository-supported command:

```bash
npm run deploy
```

That command builds the app, applies outstanding **remote D1 migrations**, and then deploys the Worker. Do not substitute a bare `wrangler deploy` for this upgrade.

If you use Cloudflare AI Gateway / Vertex, review `SETUP.md`: the direct Gemini API key is now optional for that configuration, while all gateway settings must be complete.

## Notes worth knowing

- Cellar holdings are intentionally invisible to tasted-wine statistics until a bottle is opened.
- Existing stale derived tags are repaired when each wine is next saved; this release does not run a bulk tag rewrite.
- Grape synonym grouping and prestige-Champagne ageing exceptions are curated tables. Unknown names fall back conservatively rather than being guessed.
- Vintage lookup is intentionally on demand. A cellar of several distinct grand crus from one year may require several grounded lookups because each named site can have its own vintage assessment.
- Region anchors are curated and incomplete; an unknown region falls back to the country marker.
