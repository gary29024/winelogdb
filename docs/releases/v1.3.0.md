# WineLogDB v1.3.0

**Release date:** 2026-09-23

WineLogDB 1.3 is the release where the app becomes genuinely **multi-user** and gains a durable external wine-identity layer.

The release brings Google-authenticated member accounts, friend tagging and sharing that behaves like part of the recipient's own Journal, sponsored member AI access with a configurable weekly research allowance, and a full LWIN/ELID reference system for matching and enriching logged wines without making external catalogues the application's source of truth.

It also completes a large Journal/Account/Owner redesign, extends Smart Search to shared wines, adds verified Burgundy Atlas links, centralizes the AI model policy, and hardens the queue/backfill paths that now do more of WineLog's long-running work.

## Highlights

### WineLog is now multi-user without copying a friend's wine into your account

The multi-user architecture that was intentionally excluded from v1.2.0 is now shipped.

- Google sign-in and authenticated sessions support an invite-only owner/member model.
- Wine, research, storage and account data remain owner-scoped.
- Friend relationships and wine sharing are separate: becoming friends does not expose a library automatically.
- A wine can be tagged from the wine detail page, Journal multi-select, or an entire tasting.
- Per-friend defaults can automatically tag newly logged wines.
- Sharing a tasting applies to wines already in the tasting and wines added later.
- Shared wines appear directly in the recipient's **Journal, Passport, Insights and Wine Collections** as read-only virtual entries rather than as copied database records or a separate inbox.
- A recipient can favourite a shared wine and record their own experience data without changing the source owner's record.
- Shared producers appear through a recipient read model, so recognition can treat a producer already visible through a friend's wine as known without duplicating producer identities.

The shared payload is intentionally narrower than the owner's wine record. Private owner-only fields such as personal tasting notes, score, price, venue and exact location are not published as the source owner's experience. The recipient's own experience fields remain theirs.

Shared photos now reuse the owner's canonical R2 image and the same persistent thumbnail used by the owner instead of producing a separate R2 copy for every recipient. Authorization is still checked against the shared wine. This avoids incremental storage per recipient, but it also means the full-size shared image is the original uploaded file; embedded EXIF/GPS data in that image can therefore remain available to the specifically selected accepted friend.

### Member AI is sponsored and predictable

The pilot credit UI has been replaced by the intended launch policy.

For normal members:

- Single Scan, Group Photo, Batch Scan and tasting-sheet recognition are sponsored.
- Smart Search is included and usage-metered.
- Wine Deep Search, individual producer research and Vintage Window share one configurable weekly allowance.
- The default allowance is **2 user-facing research runs per week**.
- One user-facing research request counts once even when the implementation fans out into multiple internal research scopes.
- Retries and idempotent replays stay inside the same claim.
- Cached or friend-reused research does not consume another run.
- Batch Deep Search remains owner-only.

The week runs from Monday 00:00 UTC to the following Monday 00:00 UTC.

The owner remains exempt from member allowance restrictions and continues to see provider-cost/accounting detail. Members see a simplified usage summary without provider-dollar or other-member information.

Member-facing recognition/research screens also stop exposing model, provider, fallback, compression and gateway plumbing. Operational failures expose a **Support ID** that can be used for investigation.

### LWIN becomes the external product identity layer

WineLog now has a production LWIN reference layer designed to enrich identity without making Liv-ex data the application's authority.

Bulk LWIN data is stored once in versioned, producer-keyed R2 shards rather than consuming D1 writes for hundreds of thousands of reference rows. D1 stores only lightweight sync state plus external IDs and snapshots actually linked to WineLog wines.

The importer supports the downloaded LWIN workbook directly:

```powershell
npm run lwin:build-import -- "C:\WineLogData\LWINdatabase.xlsx"
npm run lwin:import -- "C:\WineLogData\LWINdatabase.xlsx"
```

The import pipeline:

- validates the official workbook contract;
- normalizes Excel numeric IDs;
- preserves Live, Combined and Deleted states;
- follows chained Combined redirects to the current Live identity;
- publishes content-addressed R2 versions atomically by switching the manifest last;
- keeps older versions available for rollback.

Wine recognition now distinguishes:

- vintage;
- non-vintage;
- multi-vintage;
- unknown vintage;

and can carry explicit release/edition identity such as `171ème Édition`, `MV20` or `90-21`.

WineLog's own wine, producer and cuvée IDs remain authoritative. A failed or unavailable reference lookup cannot block a valid wine save.

### Existing wines can be matched and enriched conservatively

Owner Controls now provides background matching for wines logged before LWIN went live.

The first pass is deterministic and local. It:

- scans existing wines through the durable rollout queue;
- skips manual identities and wines already linked;
- uses the imported R2 catalogue only;
- persists only a unique compatible match;
- leaves ambiguous or unmatched wines untouched;
- preserves notes, photos, ratings, prices and other personal data.

An optional second pass handles harder unresolved cases. Candidate narrowing still happens locally; only uncertain candidate sets are sent to Gemini 3.1 Flash Lite through the normal AI Gateway/Vertex Flex path. The model can select only from supplied LWIN7 candidates or reject them all. A high-confidence answer is still re-run through the canonical resolver before persistence.

Backfills are resumable. Wine updates and checkpoints are committed together, with leases, stale-message checks and recovery so interruption does not silently restart large sections of work.

Accepted reference snapshots can fill supported missing facts and expose catalogue metadata such as product type, subtype, classification, region/sub-region and other reference facts. Populated wine fields, explicit overrides and manual decisions are preserved rather than overwritten.

### LWIN corrections are reviewable instead of automatic

The identity UI has been redesigned around explicit review rather than making the user manage reference codes during ordinary logging.

- Clear matches stay on the normal one-tap save path.
- If a proposed reference conflicts with populated wine fields, the user gets an explicit same-wine confirmation.
- Owners can preview and manually link a different LWIN7.
- A bad match can be rejected; rejection clears reference metadata but preserves personal wine data and is remembered so automatic backfills do not immediately restore it.
- Producer-name corrections can be previewed and applied across linked wines while preserving producer/cuvée identities, LWIN links, wine names, tasting data and research.
- Existing producer collisions still require the established merge flow; similar producer names are not silently merged.

The edit page keeps the normal WineLog fields primary and puts LWIN status, comparison and matching tools in a compact reference section.

### ELID is now populated from the public registry

ELID remains complementary to LWIN rather than replacing it.

WineLog does not fabricate ELIDs. The registry importer reads only public identity facts, respects crawl boundaries, and publishes versioned reference data without copying ELID editorial or technical content.

By the current release baseline, the production registry sync had published and verified **5,599 public registry identifiers from 426 producers**, and the saved-wine refresh completed without errors.

Existing accepted identities can therefore gain a missing verified ELID during refresh without replacing stored IDs, manual rejections or user decisions.

### Shared wines now participate in Smart Search

Smart Search previously indexed only wines logged by the current account. That meant a member whose Journal was mostly shared wines could receive no semantic results.

v1.3 indexes the member's own wines plus currently visible shared wines under the recipient's search index.

For a shared wine, the semantic document is built only from:

- wine facts the recipient is allowed to see;
- the recipient's own notes;
- the recipient's own score;
- the recipient's own tasting name.

The source owner's private notes and score are not indexed for the recipient.

If the source wine changes or the recipient updates their own experience, the shared document can refresh. If sharing is withdrawn, the semantic candidate is removed.

Smart Search also now caches ranked query candidates for a bounded period and binds the cache to a semantic-index revision, avoiding repeat embedding/vector work after navigating into a result and back while still invalidating safely after the index changes.

### Journal, Account and Owner Controls received a full layout pass

The Journal, Account & friends and Owner Controls pages now share a more compact, mobile-first information architecture.

Journal improvements include:

- removable filter chips;
- clearer empty and no-match states;
- recovery from stale saved page offsets after deleting or unsharing wines;
- pagination hidden when there is only one page;
- dedicated **Cellar** and **Favorites** titles/descriptions;
- stable mobile header height so scope tabs do not jump when switching tabs;
- a consistent folding Filters control;
- result count aligned beside Filters.

Account is split into focused Profile, Friends and AI usage sections.

Owner Controls is split into Members, Usage, Access & budgets and Maintenance, with operational warnings retained and member-usage deep links preserved.

Shared wine cards use a visual shared-state treatment rather than repeatedly printing attribution on every card. Wine detail retains a small attribution indicator while reusing the same wine-facts definition as the owner's detail page.

### Owner and shared wine details now stay in sync

The owner and shared detail pages now render common wine facts from one definition, so bottle facts do not drift between the two surfaces.

Shared wine detail can include bottle-level facts such as:

- denomination/appellation;
- grape percentages;
- the recorded identity line;
- sparkling/Champagne release details;
- classification styling.

Private owner experience and operational diagnostics remain outside the shared type boundary.

Deep Search source summaries now attribute Google Search grounding redirects back to the real publisher domains when safely identifiable, so counts reflect actual websites instead of collapsing every source into `vertexaisearch.cloud.google.com`.

Champagne production details sit with the main wine facts, and the full-screen photo viewer now correctly covers the whole phone viewport.

### Burgundy Atlas links move from Grand Cru-only to a broader Burgundy map layer

WineLog can now link relevant Burgundy identities directly to verified Burgundy Atlas destinations.

The first pass added all 33 Grand Cru appellations. The current mapping extends coverage to:

- **630** Premier Cru plot destinations;
- **43** village appellations;
- **29** Premier Cru appellations.

A named Premier Cru can link to its specific plot when the identity is sufficiently certain. Village wines link to the village appellation. A Premier Cru without one safe plot can fall back to the Premier Cru appellation, but never to the wrong village or Grand Cru tier.

Ambiguous, conflicting or unmapped identities deliberately receive no link.

The mapping is static and verified ahead of time. Opening a WineLog wine does not make a runtime Burgundy Atlas API request and does not use AI for the mapping.

### AI routing is centralized and long-running work is safer

WineLog's active AI model choices now live in one policy module, while the app deliberately keeps capability-specific transports instead of introducing a generic routing abstraction that would not replace the current multimodal, grounded-search, Vertex Flex/Batch and Workers AI paths.

The release baseline uses:

- Gemini 3.1 Flash Lite on low-cost recognition and appropriate low-cost paths;
- Gemini 3.8 Flash for synchronous recognition escalation;
- Gemini 3.8 -> 3.7 Flash for grounded wine/producer research fallback;
- Gemini 3.1 Flash Lite -> 3.8 Flash for Vintage Intelligence;
- GLM-4.7-Flash -> Workers AI Qwen3-30B-A3B -> grounded Gemini for Producer Range extraction;
- Qwen3 embeddings / optional Gemini Embeddings for Smart Search.

Workers AI's text fallback moved to Qwen3-30B-A3B.

Vertex/Gemini batch execution now shares a bounded execution budget, persists timeout failures and can enter the normal recovery path instead of allowing a slow provider response to consume an entire queue invocation and disappear without a terminal state.

The LWIN AI rollout was also reduced to one wine per queue message so every successful wine is durably checkpointed before the next one is chained.

### Champagne extraction and AI usage follow-ups

The Champagne/sparkling work introduced in v1.2 received several production hardening passes:

- reopening an in-flight extraction restores the exact source-photo selection;
- extracted text is requested in concise English and normalized into sensible capitalization;
- Champagne extraction is metered separately from generic Batch Scan usage;
- Vintage Window history recovers meaningful place/year/style labels instead of generic names;
- member Batch Scan now carries recognized sparkling details into the review form;
- recognition response plumbing no longer leaks internal credit metadata into strict recognition schemas.

For a self-hosted deployment, back up D1/R2 as appropriate and use the repository-supported command:

```bash
npm run deploy
```

That command builds the application, applies outstanding **remote D1 migrations**, and only then deploys the Worker. Do not replace it with a bare `wrangler deploy` for this upgrade.

Multi-user deployments additionally need the documented authentication/runtime configuration, including a valid `APP_URL`, sufficiently strong `AUTH_SECRET`, owner identity configuration and Google OAuth client setup. Member invitations and action access remain owner-controlled.

LWIN/ELID reference catalogues are separate operational data. Deploying the code does not require re-importing a reference snapshot that is already current in R2.

## Notes worth knowing

- **Sharing is not copying.** A shared wine remains owned by its source account; the recipient sees a privacy-limited read model plus recipient-owned experience/preferences.
- **Shared full-size photos reuse the original object.** This is storage-efficient but means embedded image metadata can travel to the accepted friend who was explicitly given access.
- **Member research allowance is configurable.** The shipped default is 2 runs/week, not a hard-coded product limit.
- **Smart Search on shared wines is privacy-scoped.** It never uses the source owner's private notes/score in the recipient's semantic document.
- **LWIN/ELID are references, not WineLog's primary keys.** Personal fields, WineLog identities and manual decisions take precedence over imported catalogue data.
- **AI-assisted LWIN backfill is owner-triggered rollout work.** It is not part of the normal recognition hot path and the model cannot invent an external ID.
- **Ambiguity is preserved.** LWIN and Burgundy Atlas integrations deliberately leave uncertain cases unresolved instead of making a plausible-looking guess.
